Osintly separates Personal workspaces from organization workspaces. Organization permissions are checked for every protected action, not only when an interface button is visible.

---

## Workspace modes

<CardGroup cols={2}>
  <Card title="Personal workspace" icon="user">

  </Card>
  <Card title="Organization workspace" icon="buildings">
    Members use a shared plan, credits, history, API account, and organization billing.

## Roles

| Capability | Owner | Admin | Member |
|---|---:|---:|---:|
| View organization history | Yes | Yes | Yes |
| View organization usage | Yes | Yes | No |
| Invite members | Yes | Yes | No |
| Remove members | Yes | Yes* | No |
| Change member roles | Yes | No | No |
| Manage organization API keys | Yes | Yes | No |
| Manage billing, SSO, ownership, or deletion | Yes | No | No |

\* Admins can remove members but cannot remove the owner or another admin.

---

## Billing and credit behavior

When a member launches a full search in an organization workspace, one credit is reserved from the organization's shared allowance. The same organization subscription determines plan access for all members of that workspace.

- Personal subscriptions and credits are never used automatically in the organization.
- An organization subscription does not upgrade a member's Personal workspace.
- A member in several organizations gets a separate role and organization allowance in each one.
- The owner is the only role that can manage organization billing.

<Note>
Tool lookup overrides also use the organization allowance when the organization is active. See [Tool usage limits](/tools-reference/usage-limits).
</Note>

## Access behavior

<AccordionGroup>
  <Accordion title="History visibility" icon="clock-rotate-left">
    Organization history is visible to all organization members and identifies the member who created each entry. Personal history stays private to its owner.
  </Accordion>
  <Accordion title="Workspace isolation" icon="buildings">
    Selecting an organization does not expose Personal data, another organization, or legacy Team data. A workspace preference is rechecked server-side and is never treated as authorization by itself.
  </Accordion>
  <Accordion title="Legacy Monitoring" icon="eye">
    The current Monitoring experience is being retired in favor of Security Watch. Do not use legacy monitor access as the basis for a new operational workflow.
  </Accordion>
</AccordionGroup>

---

## Operational recommendations

- Keep the owner role limited to people responsible for billing and lifecycle actions.
- Use the workspace switcher deliberately before launching a search or creating an API key.
- Review members, pending invitations, usage, and API keys regularly.
